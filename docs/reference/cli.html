CLI Reference

llmux ships a single console script (pyproject.toml → [project.scripts] llmux = "tui.cli:main"). Running it with no arguments launches the TUI; every subcommand is a headless, scriptable equivalent of a TUI action. 

llmux                      # launch the interactive TUI (default)
llmux tui                  # launch the TUI explicitly
llmux top [PROFILE]        # btop-style monitor in a plain terminal (no TUI)
llmux <group> <command>    # headless control
llmux <alias>              # top-level shortcut (see below)
llmux --version            # print the installed version and exit

All commands accept -h / --help, and --version / -V prints the installed llmux version. The CLI is built with Typer; the option tables below are extracted directly from the typer.Option / typer.Argument definitions in tui/cli/.

How to run it

Examples use uv run llmux … (the project's standard uv workflow). If you installed the tool globally with uv tool install, drop the uv run prefix and call llmux … directly.

Common concepts

top

The btop-style system monitor, rendered in a plain terminal without the Textual TUI. Good for low-bandwidth SSH or dumb terminals. Every GPU is shown always — util, memory, temperature, power, PCIe rx/tx — whether or not anything is running, plus a panel per running model (throughput and KV-cache braille graphs, cache-hit, requests, latency percentiles: TTFT/E2E p50/p95/p99 and phases). With no argument it shows every running model; pass a profile name to narrow it to that one. Press q or Ctrl+C to exit. The same monitor is reachable inside the TUI with the t key.

llmux top [PROFILE]

Backend detection

Profile names are globally unique across both backends. Most commands resolve the matching backend (vllm or llamacpp) automatically by scanning profiles.yaml:

  • If the name exists, its backend is used.
  • Pass --backend / -b to require a specific backend explicitly.
  • If it exists in neither, the command fails with a clear usage error.

--backend always wins when supplied.

Exit codes

Lifecycle commands propagate the underlying docker / docker compose exit code. Ctrl-C while streaming (up, logs, build-dev) exits with 130. system env-check exits 1 when .env.common is missing or has issues.

container — container lifecycle

llmux container up|prepare|down|logs|ps|benchmark|stats|render-env …

Start, stop, inspect, benchmark, monitor, and re-render profile containers. Every container command except the grouped namespace itself is also exposed through the corresponding top-level alias.

container up

Start a profile's container. Streams docker compose output to stdout.

llmux container up PROFILE [OPTIONS]
ArgumentDescription
PROFILEProfile name (from profiles.yaml). Required.
OptionDefaultBackendDescription
--backend, -bauto-detectbothForce backend (vllm, llamacpp); auto-detect if omitted.
--tag, -t""bothImage tag override. vLLM: vllm/vllm-openai:<tag> or vllm-dev:<tag> with --dev. llama.cpp: full image ref (e.g. ghcr.io/foo/bar:v1) or llamacpp-dev:<tag> with --dev. Empty = profile's pinned image_tag or backend default.
--devFalsebothUse the locally-built dev image (vllm-dev:<tag> for vLLM, llamacpp-dev:<tag> for llama.cpp). Triggers a one-off build if the tag is missing locally or was built from a different repo/branch.
--default-imageFalsebothMirrors the TUI's "Default Image" selection — explicitly drop the profile's pinned image_tag for this run only and fall back to the compose default. Useful when a profile has a stale dev tag pinned. Mutually exclusive with --dev.
--pullFalsebothForce --pull always for non-dev images. Locally built dev images remain --pull never.
--repo-urlfrom .env.commonboth--dev only: override the source repo URL (default from VLLM_REPO_URL / LLAMACPP_REPO_URL).
--branchfrom .env.commonboth--dev only: override the source branch (default from VLLM_BRANCH / LLAMACPP_BRANCH).
--forceFalsebothAllow a detected GPU overlap. Port conflicts and failed port probes always abort.
--replaceFalsebothStop managed models sharing the target GPUs, verify their exit, then start this profile. Cannot be combined with --force.
 
# Start a vLLM profile (official image, highest local versioned tag)
uv run llmux container up qwen3-0-6b

# Start it from a locally-built dev image
uv run llmux container up qwen3-0-6b --dev --tag main-20260515

# One-off: ignore a stale pinned image_tag and use the compose default
uv run llmux up qwen3-0-6b --default-image

# Start a llama.cpp profile with an explicit backend
uv run llmux up gemma-3-4b --backend llamacpp

# llama.cpp dev image from a personal fork
uv run llmux up gemma-3-4b --dev \
    --repo-url https://github.com/me/llama.cpp.git --branch master

Pinning a dev image to a profile

To persist a dev image choice, edit the profile with llmux profile edit <name> --image-tag llamacpp-dev:<tag> (or vllm-dev:<tag>). container up then layers the appropriate compose override automatically. Use --default-image to bypass the pin for a single run.

container prepare

Download the model and render the runtime files — without starting the server. Everything up does up to docker compose up: renders the profile env (plus llama.cpp's command override), makes sure the image is on disk (pulling it if not), then downloads the weights into the HF cache from HF_CACHE_PATH. No container is left running and no GPU is touched.

llmux container prepare PROFILE [OPTIONS]
ArgumentDescription
PROFILEProfile name (from profiles.yaml). Required.
OptionDefaultDescription
--backend, -bauto-detectForce backend; auto-detect if omitted.
--max-workers, -wfrom PREPARE_MAX_WORKERSPositive parallel download connection count for this run. Omit it to use .env.common; an empty shared setting leaves the downloader library default unchanged.
 
uv run llmux prepare qwen3-0-6b
uv run llmux prepare gemma-3-4b --backend llamacpp

How the download runs

vLLM runs huggingface_hub.snapshot_download inside the resolved serving image. llama.cpp instead runs the same library inside PREPARE_DOWNLOADER_IMAGE, which is required only for llama.cpp prepare. Both are throwaway downloader containers and llmux never needs an hf CLI on the host.

List profiles and their container status across backends.

container benchmark · bench

Benchmark a running container's generation speed via /v1/chat/completions. A warmup call is discarded, then --runs measured calls report the median tok/s (a single cold call conflates model warmup with steady-state decode).

llmux bench PROFILE [OPTIONS]
OptionDefaultDescription
--backend, -bautoForce backend; auto-detect if omitted.
--prompt(built-in)Prompt sent to the chat endpoint.
--max-tokens200max_tokens for the request.
--runs3Measured runs; the reported figure is their median.
--warmup1Warmup runs discarded before measuring.
--jsonFalseEmit a JSON record (per-run + median/min/max) instead of a human line.
 
uv run llmux bench qwen3-0-6b --runs 5
uv run llmux bench qwen3-0-6b --json

container stats · stats

Live token throughput (tok/s) for every running container, polled from its Prometheus /metrics endpoint. Rates are deltas between successive samples, so the first line appears one interval in. An unavailable metric reads n/a; an HTTP request failure is reported as an error rather than displayed as normal missing data.

llmux stats [OPTIONS]
OptionDefaultDescription
--backend, -ballLimit to one backend; show all if omitted.
--interval, -i2.0Seconds between /metrics samples.
--onceFalseTake two samples one interval apart, print one tick, then exit.
--jsonFalseEmit one compact JSON line per tick (NDJSON).
 
uv run llmux stats                 # live, Ctrl-C to stop
uv run llmux stats --once --json   # one machine-readable sample

llama.cpp needs --metrics

vLLM exposes /metrics by default; llama.cpp does not, so llmux injects --metrics into every llama-server command it renders. The same figures drive the live tok/s column on the TUI dashboard.

config — config (YAML) CRUD

llmux config list|show|new|edit|clone|rename|flags|from-recipe|delete …

Per-model engine configs live in config/<backend>/<name>.yaml:

  • vLLM — config/vllm/<name>.yaml: model: + gpu-memory-utilization: plus arbitrary vllm serve flags.
  • llama.cpp — config/llamacpp/<name>.yaml: a flat dict of llama-server flags.

New config names (new, clone destination, rename destination, and recipe --name) must match ^[a-z0-9][a-z0-9_-]*$. Read/edit/delete and clone-source lookups also accept legacy on-disk names matching ^[a-zA-Z0-9][a-zA-Z0-9._-]*$, so an older or hand-written file can still be inspected and removed. If the same name exists in both backends, disambiguate with --backend.

config from-recipe

Create a vLLM config from the model's official vllm-project/recipes recipe. The TUI shows an interactive review window (see Import a vLLM recipe); this headless form picks a variant with --variant, or auto-picks the highest-quality one that fits the detected GPU.

llmux config from-recipe MODEL_ID [OPTIONS]
OptionDefaultDescription
--listFalseList the recipe's variants + features and exit.
--variantautoPrecision variant (default/fp8/awq/…). Auto-picks a GPU-fitting one if omitted.
--feature(none)Repeatable: opt-in feature to enable (e.g. reasoning).
--name, -nautoConfig name (derived from the model id if omitted).
--jsonFalsePreview the resulting config as JSON without writing.
--overwriteFalseOverwrite if the config already exists.
--recipe-from(MODEL_ID)Fetch the recipe of a different model (e.g. the base model of a quantized checkpoint). The config's model stays MODEL_ID; only the recipe's flags are borrowed, and a variant's checkpoint swap is ignored.
--mergeFalseMerge the recipe's params into an existing config instead of replacing it — recipe values win, other keys are kept. Mirrors the TUI's Fetch vLLM recipe button inside Edit Config. Mutually exclusive with --overwrite.
 
uv run llmux config from-recipe Qwen/Qwen3-32B --list
uv run llmux config from-recipe Qwen/Qwen3-32B --variant fp8 --feature reasoning
uv run llmux config from-recipe Qwen/Qwen3-32B --variant awq --json

# Borrow the base model's recipe for a quantized checkpoint
uv run llmux config from-recipe cpatonn/Qwen3-32B-AWQ \
    --recipe-from Qwen/Qwen3-32B --variant awq

# Merge into a config you already have
uv run llmux config from-recipe Qwen/Qwen3-32B --name my-model --merge

Keep credentials out of refs and command lines

--repo-url rejects an HTTP(S) URL containing userinfo, a query, or a fragment; use a credential helper or a credential-free SSH URL instead. A username-only SSH authority such as ssh://git@host/path is allowed. Docker image inputs reject URL schemes, userinfo, query strings, fragments, and whitespace before invoking Docker.

See Dev Builds for the full workflow, and Architecture for how the pipeline works.

system gpu

Print an nvidia-smi summary, one row per GPU. Also available as the top-level alias llmux gpu.

llmux system gpu [OPTIONS]
OptionDefaultDescription
--jsonFalseEmit JSON instead of a table.

Columns: index, name, memory_used, memory_total, utilization, temperature. Prints (no GPUs detected — is nvidia-smi installed?) if none are found.

system mem-estimate

Estimate a Hugging Face model's VRAM footprint via hf-mem — the same engine the TUI's memory estimator uses. Reads HF_TOKEN from .env.common (or the environment) for gated models.

llmux system mem-estimate MODEL_ID [OPTIONS]
ArgumentDescription
MODEL_IDHugging Face model id, e.g. Qwen/Qwen3-8B. Required.
OptionDefaultDescription
--jsonFalseEmit the parsed estimate and per-GPU fit rows as one JSON object.
 
uv run llmux system mem-estimate Qwen/Qwen3-8B
# → ~17.2GB (model: 15.3GB + KV: 1.9GB)

JSON output sets status to ok, over, or error. A malformed, non-finite, or non-positive GPU memory reading produces an error row with total_gb, ratio, and over set to null. Unless another known GPU is over capacity, aggregate any_over is also null. Text output labels the row UNKNOWN; either format exits 1 when any GPU memory reading is unknown.

system disk

Show backend storage and df -h usage. vLLM reports its configured host Hugging Face cache; if the cache has not been created yet, the command measures the nearest existing ancestor and still succeeds. Its JSON output distinguishes this with hf_cache_exists: false and identifies the measured path as df_target. llama.cpp reports its model directory, GGUF inventory, and HF GGUF cache. The JSON success and failure payloads both identify the selected backend.

llmux system disk [OPTIONS]
OptionDefaultDescription
--backend, -bllamacppvllm or llamacpp.
--jsonFalseEmit a backend-tagged storage object.
 
uv run llmux system disk --backend llamacpp

# GGUF files: 2 (total 17.1 GB)

uv run llmux system disk --backend vllm --json

system env-check

Validate .env.common and report key paths. Checks that the file exists, is owner-only rather than group/world-accessible, and that required paths such as HF_CACHE_PATH are set and absolute. HF_TOKEN is optional, and the runtime injects the selected vLLM version at start time. Also available as llmux env-check.

llmux system env-check [OPTIONS]
OptionDefaultDescription
--jsonFalseEmit JSON findings instead of a text report.

Exits 0 when everything checks out, including when only non-fatal warnings are present, and exits 1 when .env.common is missing or any issue is found. Human output prints non-fatal messages under Warnings: before Status: OK. JSON preserves them in warnings, keeps issues empty, and reports status: ok. Text output masks HF_TOKEN; JSON exposes only set and length, never the token value.

uv run llmux env-check
uv run llmux system env-check --json

See .env.common Reference for every variable this command validates.

update — check for a newer llmux

Ask GitHub whether this checkout is behind the latest Release, and update to it. llmux already checks on every interactive start (only a failed lookup backs off for 15 minutes), so this command is for asking on demand — right after a release, or from a script.

llmux update [OPTIONS]
OptionDefaultDescription
--checkFalseOnly report; never touch the checkout.
--yes, -yFalseUpdate without asking for confirmation.
--jsonFalseEmit exactly one JSON document. Use with --check for status only or --yes to apply an update without a prompt.
 
llmux update --check          # "llmux is up to date (v2.6.0)."
llmux update --check --json   # machine-readable status
llmux update -y               # pull + refresh the installed tool, no prompt

Exit codes: 0 when the state is known (up to date, or reported/applied), 1 when the check could not be completed (offline, rate-limited, not a git checkout, shallow clone) or the update failed. An update is refused — with the reason — when the checkout is not on a clean main; pull it yourself there.

If the Git fast-forward succeeds but refreshing the installed uv tool fails, the checkout has already advanced but the update still exits 1. The error prints the manual refresh command; the TUI reports the same partial failure and stays open.

The TUI has the same action on U.
